# Migrate backend selection explicitly without rewriting historical execution

Immutable Check profile pins make changing default execution backends insufficient for existing work. Permit explicit validated profile migration only after ownership and resource reconciliation, retain original and replacement selections as history, and invalidate freshness and stale evidence; preserve Check identity, description, order and every existing Assignment's original profile/backend binding.

This deliberately introduces a narrow exception to immutable effective Check pins rather than silently interpreting Herdr profiles as durable profiles or abandoning existing Tasks. Rollout and rollback affect new execution only: live or uncertain Assignments always recover or retire through their original backend, and another-backend successor requires safe cleanup and explicit compatible selection.

Representation: `record_checks.profile_revision` stays the original pin and is never updated. Append-only `check_profile_migrations` / `check_profile_migration_changes` rows (immutable and undeletable by trigger) record the operation identity, request digest, actor, message, prior and new revision per Check and the work generation before and after. A Check's effective revision is its latest migration change, else its original pin; dispatch, Execution Mode validation and Stack validation all read the effective revision. One migration commits in a single immediate transaction with the Task's freshness invalidation, so a failure leaves neither. An exact retry by operation ID returns the original receipt without advancing freshness, even after later changes; the same ID with different content conflicts. This number was the next available when recorded; the filesystem Spec's proposed 0014 was provisional because 0012 absorbed the recovery decision.
